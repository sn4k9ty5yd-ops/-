## 0. 確定事項（ユーザー回答・参考画像より）

- 参考画像: 出勤簿（スタッフごとに「適用／入店／退店／休憩／実働」の5段、右端に合計、期間は令和表記 R8/10/16〜11/15）と、月間カレンダー型シフト表（有給=黄、店休日・祝日=ピンク、土=青、日=赤）。
- 店舗（5つ）: ATENA / ATENA六本松 / ATENA福津 / Organ / ATENA AVEDA SAKURAMACHI
- 勤務形態（早番・遅番など）は**なし**。入店・退店時刻の自由入力。
- 休憩: 時間の長さに応じたルールあり（例: 10:00-19:00→休憩1:00、10:00-20:00→休憩2:00）。→ルール詳細は要確認。
- シフトと出勤簿は**各店の店長が作成**し、オフィス事務員（同じ会社の社員）に提出→オフィスが最終確認。アプリ内で完結させる。
- 閲覧範囲: スタッフ＝自店舗のみ／店長＝全店舗を閲覧／管理者（1名）＝全店舗。
- 管理者は1名、ユーザー本人は店長。他店への応援はほぼなし（1人1店舗を基本とする）。
- スタッフ全員がメールアドレスを持つ → ログインは「会社ID＋メール＋パスワード」。
- 残業代・割増の計算は**不要**（実働時間の集計のみ）。
- 有給は個人ごとに管理（有給の日数管理が必要か要確認）。

## 1. 要件整理

### 1.1 ゴール
Excel・メール・LINEで行っている「希望休提出 → シフト作成 → 確定 → 公開 → 出勤簿 → 労働時間集計 → オフィス提出」を1つのWebアプリに集約する。
複数企業が利用できるマルチテナントSaaSとして設計し、最初は1社5店舗で運用する。

### 1.2 MVP（第一段階）スコープ
1. ログイン
2. 会社・店舗管理
3. スタッフ管理
4. シフト期間管理
5. 希望休提出
6. シフト作成
7. シフト確定
8. スタッフへの公開
9. スマホでシフト確認
10. 全員の休み確認
11. 出勤簿（管理画面からの入力・修正）
12. Excel出力

### 1.3 MVPに含めないもの（構造だけ用意）
- スマホからの出勤/退勤ボタン（テーブルは対応済み、UIは第二段階）
- プッシュ通知（通知テーブルとイベント発行は用意、配信はメール→Web→Pushの順）
- ネイティブアプリ（Capacitorでラップ可能な構成にする）
- オフィス担当者向けの高度な機能（MVPでは閲覧＋提出/確認ステータスのみ）

### 1.4 非機能要件
| 項目 | 方針 |
|---|---|
| セキュリティ | テナント分離をDB層（Row Level Security）で強制。最優先事項 |
| 対応端末 | iPhone Safari / PWAを第一優先。管理者はPCブラウザも |
| 可用性 | マネージドサービス利用。日次バックアップ |
| 個人情報 | 通信TLS、パスワードはArgon2/bcryptハッシュ、監査ログ保持 |
| 国際化 | 当面は日本語のみ。文言は辞書化しておく |
| 時刻 | タイムゾーンはAsia/Tokyo固定でも、会社設定として保持 |

## 2. 技術構成（提案）

| レイヤ | 提案 | 理由 |
|---|---|---|
| フロント | **Next.js (TypeScript) + Tailwind + PWA** | モバイルファースト、将来Capacitorでアプリ化しやすい |
| バックエンド/DB | **Supabase（PostgreSQL + Auth + RLS）** | RLSで会社単位の分離をDB側で強制できる。基本無料枠あり |
| Excel出力 | exceljs（サーバー側生成） | 既存Excel書式に近づけやすい |
| メール | Resend 等 | 通知メール |
| ホスティング | Vercel（フロント）+ Supabase | 低コストで開始可能 |
| アプリ化 | Capacitor（iOS/Android）、通知はAPNs/FCM | Webコードをほぼ流用 |
| テスト | Vitest + Playwright + **RLSの分離テスト** | 「他社が見えない」ことを自動テストで保証 |

代替案: 自前のNode/NestJS + PostgreSQL。自由度は高いが、認証・RLS相当の分離を自作する工数とリスクが増えるため、MVPでは非推奨。

## 3. 画面設計

### 3.1 画面一覧

**共通**
- ログイン（会社ID / 社員IDまたはメール / パスワード）
- パスワード変更・再設定
- 通知一覧

**スタッフ（スマホ、ボトムタブ5つ）**
| タブ | 内容 |
|---|---|
| 今日 | 今日の自分のシフト、**今日の出勤者一覧（店舗別）** |
| シフト | 自分の月間シフト（カレンダー）。期間は16日〜翌15日 |
| みんなの休み | 日付ごと／人ごとの休み一覧。「○○さんはいつ休み？」を人名検索 |
| 希望休 | 受付中の期間の希望休を日付タップで登録。締切後は閲覧のみ |
| 出勤簿 | 自分の出勤簿・月間実働時間（将来ここに出勤/退勤ボタン） |

**店舗管理者・会社管理者（PC/スマホ）**
- ダッシュボード（期間ごとの進行状況：受付中/締切/作成中/確定/公開/提出）
- シフト期間管理（作成・日程設定・状態遷移）
- 希望休一覧（スタッフ×日付のマトリクス）
- シフト作成（店舗切替・カレンダー/マトリクス、勤務パターン、公休/有給/希望休の色分け）
- 出勤簿（スタッフ×日付、出勤・退勤・休憩・実働・備考、月計）
- スタッフ管理（登録、所属店舗、雇用区分、無効化＝退職）
- 店舗管理（会社管理者のみ）
- Excel出力
- お知らせ配信

**オフィス担当者**
- 全店舗シフト閲覧、スタッフ一覧、出勤簿閲覧
- 提出状況（未確定/確定/提出済み/確認済み）、「確認済み」にする操作

**システム管理者**
- 会社の作成・停止、会社管理者の初期発行、利用状況

### 3.2 画面遷移（概要）
```
ログイン ─┬─ スタッフ ─ 今日 / シフト / みんなの休み / 希望休 / 出勤簿
          ├─ 店舗管理者 ─ ダッシュボード ─ 期間 ─ 希望休一覧 → シフト作成 → 確定 → 公開
          │                                  └ 出勤簿 → Excel出力
          ├─ 会社管理者 ─ （上記）＋店舗管理・スタッフ管理・会社設定
          ├─ オフィス ─ 提出状況 ─ 店舗別シフト/出勤簿（閲覧・確認済み）
          └─ システム管理者 ─ 会社一覧
```

### 3.3 シフト期間のステータス遷移（店舗×期間ごと）
```
準備中 → 希望休受付中 → 受付締切 → シフト作成中 → 確定 → 公開 → 提出済み → 確認済み
```
- 受付締切後、スタッフは希望休を編集不可（管理者の代理編集は可、ログに残す）
- 「公開」前はスタッフに見えない。公開後の修正は「変更履歴」を残し通知対象にする
- 受付開始・締切日時は管理者が設定（例：10/17開始、10/24頃締切）

### 3.4 UI方針
- 大きなタップ領域（44pt以上）、1画面1目的
- 休みの種類を色＋ラベルで区別（希望休／公休／有給／その他）。色だけに依存しない
- 「今日誰が出勤？」はホームの最上段に配置
- Excelの「縦=スタッフ、横=日付」はPC管理画面で踏襲、スマホは日付縦リストに自動切替

## 4. データベース設計

全業務テーブルに `company_id` を持たせ、RLSで `company_id = 現在ユーザーの会社` を強制する。

### 4.1 テーブル一覧

**テナント・組織**
- `companies`（id, code[会社ID], name, timezone, status）
- `company_settings`（company_id, closing_rule[締め日設定: type=month_end / day_n / custom, start_day], rounding_rule, default_break_rules, 休暇種別の有効/無効）
- `stores`（id, company_id, name, code, status, sort_order）

**ユーザー・権限**
- `users`（id, auth_user_id, 氏名, メール[任意], 電話[任意]）※複数社兼務を将来許容する場合に備え、人と所属を分離
- `memberships`（id, user_id, company_id, employee_code, role_id, employment_type, hired_on, left_on, status[active/disabled]）
  - ログインキー: `(company.code, employee_code or email)`
- `membership_stores`（membership_id, store_id, is_primary）※多店舗所属可
- `roles`（id, company_id nullable, key, name）／`permissions`（key）／`role_permissions`
  - 将来のロール追加はデータ追加で対応（コード変更不要）

**シフト期間・希望休**
- `shift_periods`（id, company_id, start_date, end_date, label, request_open_at, request_close_at, target_confirm_date, target_submit_date）
- `store_period_status`（period_id, store_id, status, confirmed_at/by, published_at/by, submitted_at/by, acknowledged_at/by）
- `time_off_requests`（id, company_id, membership_id, period_id, date, type[希望休/有給/公休/その他], note, created_at, locked）

**シフト**
- `shift_patterns`（id, company_id, store_id nullable, name, start_time, end_time, break_minutes, color）
- `shifts`（id, company_id, store_id, period_id, membership_id, date, kind[work/off/paid_leave/holiday...], pattern_id nullable, start_time, end_time, break_minutes, note, version）
- `shift_changes`（変更履歴：shift_id, before, after, changed_by, changed_at）

**出勤簿**
- `attendance_records`（id, company_id, store_id, membership_id, work_date, clock_in, clock_out, break_minutes, worked_minutes[計算値], note, source[manual/app], edited_by）
- `attendance_breaks`（任意：休憩を複数回記録する場合）

**通知・運用**
- `notifications`（id, company_id, membership_id, type, payload, read_at, channel）
- `push_tokens`（membership_id, platform, token）※将来のプッシュ用
- `audit_logs`（company_id, actor, action, target, before/after, ip, at）
- `export_logs`（Excel出力の記録）

### 4.2 設計上のポイント
- 締め期間は `company_settings.closing_rule` から `shift_periods` を生成（16日〜翌15日は `start_day=16`）
- 実働時間 = 退勤 − 出勤 − 休憩。月間集計は期間単位でSQLビュー化
- 退職は削除せず `status=disabled` ＋ `left_on`。過去の出勤簿は保持
- 日跨ぎ勤務（夜勤）に備え、`clock_out` は日時型（timestamptz）

## 5. 権限設計

| 操作 | システム管理者 | 会社管理者 | 店舗管理者 | オフィス | スタッフ |
|---|---|---|---|---|---|
| 会社の作成/停止 | ○ | – | – | – | – |
| 店舗の作成/編集 | – | 自社 | – | – | – |
| スタッフ登録/無効化 | – | 自社 | 担当店舗 | – | – |
| 期間の作成/日程設定 | – | 自社 | 担当店舗 | – | – |
| 希望休 閲覧 | – | 自社全員 | 担当店舗 | 閲覧 | 本人（締切前は自分のみ） |
| 希望休 登録/編集 | – | 代理可 | 代理可 | – | 本人（受付中のみ） |
| シフト作成/編集 | – | 自社 | 担当店舗 | – | – |
| シフト確定/公開 | – | 自社 | 担当店舗 | – | – |
| 公開済シフト閲覧 | – | 自社 | 担当店舗 | 全店舗 | 自分の所属店舗（※要確認） |
| 出勤簿 閲覧 | – | 自社 | 担当店舗 | 全店舗 | 本人（※要確認） |
| 出勤簿 編集 | – | 自社 | 担当店舗 | – | 本人（第二段階、制限付き） |
| 提出/確認済み | – | 提出 | 提出 | 確認済み | – |
| Excel出力 | – | 自社 | 担当店舗 | 全店舗 | – |

- システム管理者は**他社の業務データ（シフト・出勤簿・個人情報）を原則閲覧不可**。会社の枠のみ管理（サポート用の閲覧は、会社の許可＋監査ログ付きにする案を§10で確認）
- 権限は `permissions` の組み合わせで定義し、ロール追加はデータ追加で実現

## 6. セキュリティ設計

1. **テナント分離**: 全テーブルにRLS。アプリのバグがあってもDB側で他社行が返らない
2. **認証**: パスワードはArgon2/bcrypt（Supabase Auth）。ログインは会社ID＋社員ID/メール。ログイン試行制限、短命アクセストークン＋リフレッシュトークンで安全にログイン維持
3. **無効化**: 退職者は即時ログイン不可・既存セッション失効
4. **サーバー側検証**: 権限・期間ステータス（締切後の希望休編集不可）をDB/サーバーで強制し、UIの制御に依存しない
5. **監査ログ**: シフト変更・出勤簿修正・Excel出力・権限変更を記録
6. **通信/保管**: TLS、DB暗号化、秘密情報は環境変数/シークレット管理
7. **自動テスト**: 「会社Aのユーザーで会社Bのデータを取得/更新/削除できない」テストをCI必須にする
8. 個人情報の最小化（スタッフの電話・住所は収集しない、またはオプション）

## 10. 確認したい事項

### A. 最優先
1. **参考画像（Excelシフト表・出勤簿）が届いていません**。リポジトリに画像は含まれていませんでした。再度添付、または `docs/reference/` に追加してください。Excel出力・シフト作成画面の仕様はこれに依存します。
2. **ログインID**: 会社IDは会社ごとに英数字コード（例: `salon-abc`）でよいですか？スタッフはメール無しの人もいますか？（その場合は社員IDでログイン、パスワード再設定は管理者が実施する運用になります）
3. **システム管理者は誰ですか**（あなた本人？）。サポート時に他社データを見る必要はありますか（原則なし＋許可制を推奨）。

### B. 業務ルール
4. **締め期間の「16日〜翌15日」**: 期間の呼び名は開始月（11/16〜12/15 = 「11月分」）でよいですか？
5. **希望休の上限**: 1期間あたりの希望休日数に制限はありますか？上限超過は警告のみ／登録不可のどちらですか？
6. **休みの種類**: 希望休／有給／公休／その他 の他に、必要なもの（例: 特別休暇、研修）はありますか？公休・有給の確定は管理者のみ入力でよいですか？
7. **勤務形態**: 固定の勤務パターン（例: 早番/遅番/9:00〜19:00）はありますか？それとも自由な時刻入力ですか？
8. **他店舗応援**: スタッフが複数店舗を兼務・ヘルプで他店に入ることはありますか？
9. **休憩時間の自動計算**: 例「6時間超で45分、8時間超で60分」のような法定ルールで自動入力しますか？それとも毎回手入力ですか？
10. **労働時間の端数処理**: 分単位／15分・30分丸め？ 深夜(22時〜)・残業・法定休日の割増集計は必要ですか？（MVPでは実働時間のみを推奨）

### C. 見える範囲
11. スタッフは**他店舗**のシフト・休みも見えてよいですか？（現案は所属店舗のみ）
12. スタッフ同士の**出勤簿**は本人のみ閲覧でよいですか？
13. 公開後のシフト変更時、スタッフに通知しますか？

### D. オフィス
14. オフィス担当者は会社内の1アカウント（会社に属する「オフィス」ロール）という理解でよいですか？それとも別会社（経理代行等）ですか？
15. 提出ステータスは **店舗×期間ごと** でよいですか？（現案）

### E. 事業・運用
16. 「基本無料」の想定: 無料範囲（店舗数・スタッフ数の上限など）と将来の課金方法は未定でよいですか？
17. 現行データ（スタッフ・店舗）の移行（CSV/Excel取込）はMVPに含めますか？
18. 技術構成（Next.js + Supabase + Vercel）で問題ありませんか？利用制約（日本国内リージョン希望等）はありますか？
19. 利用規約・プライバシーポリシーの用意は別途ですか？
